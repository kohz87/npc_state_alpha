* **S3 — SillyTavern 1.18.0 One-Pass Immediate Continuity Vertical:** Complete and accepted (commit `6e20e67799a65103f204b74a61881cb1920c134d` — "host: complete S3 one-pass vertical").
  * **Single shared runtime retained:** S3 adds only the SillyTavern adapter/prompt/persistence boundary. It does not create a second field registry, source resolver, application engine, commit coordinator, or state model. The accepted S2 `src/runtime/` and `src/state/` architecture remains authoritative.
  * **Extension artifact:** `manifest.json` uses `loading_order: 100`, `js: "index.js"`, and `generate_interceptor: "npc_state_alpha_generate_interceptor"`. Root `index.js` exports `initExtension`/`getActiveAdapter`, auto-bootstraps when SillyTavern is present, and retries idempotent initialization if the first import occurs before a chat is selected.
  * **Actual SillyTavern capability surface:** Verified against SillyTavern 1.18.0 commit `8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8`. S3 uses the real manifest `generate_interceptor`, `getContext()`, `eventSource`/`eventTypes`, `setExtensionPrompt`, `updateMessageBlock`, `getRequestHeaders`, chat metadata, `streamingProcessor`, and the official chat-save endpoints. Welcome-screen initialization requires stable extension/event/persistence surfaces but not a selected chat; source capture and persistence still fail closed without a real chat identity.
  * **Host lifecycle boundaries:** `MESSAGE_RECEIVED` is the state-candidate/commit boundary. `CHARACTER_MESSAGE_RENDERED` is the presentation cleanup/reconciliation boundary. `STREAM_TOKEN_RECEIVED` never mutates state. `GENERATION_STOPPED`, `MESSAGE_SWIPED`, `MESSAGE_EDITED`, `MESSAGE_UPDATED`, `MESSAGE_DELETED`, `MESSAGE_SWIPE_DELETED`, and `CHAT_CHANGED`/`CHAT_LOADED` invalidate or isolate in-flight work as appropriate. `GENERATION_ENDED` is intentionally not treated as a commit signal.
  * **Finalized-only streaming:** For an exact matching `streamingProcessor.messageId`, a candidate is rejected if the processor is stopped, aborted, or not finished. Successful streaming reaches `MESSAGE_RECEIVED` only after the processor is finished. Non-streaming candidates are not poisoned by unrelated/stale processor state.
  * **Generation interceptor and exact host provenance:** The interceptor maps the derived/core-chat current user message back to the authoritative raw `ctx.chat` record using role, exact content, swipe identity, and preceding lineage; ambiguous mappings fail closed. It stores real chat identity, message position, role, canonical content fingerprint, swipe/revision identity where available, and exact preceding lineage for `current:user`/`current:assistant` resolution.
  * **Machine transport semantics:** A structurally recognized single terminal `<npc_state_alpha_v1>...</npc_state_alpha_v1>` block is transport, not later narrative evidence, even if its JSON/schema fails. Such failed transport remains intact in raw host message bytes for diagnosis/recovery but is excluded non-destructively from future prompt/history projection. Missing, malformed, truncated, duplicate, or non-terminal transport never triggers regeneration, a fallback scanner, or another provider call.
  * **Strict immediate authority:** One-pass proposals are parsed and validated by the S1 C04 schema and committed through `CommitCoordinator` as `WRITERS.ONE_PASS`. S3 may update only C02 immediate-owned identity/admission, presence/activity, live state (`status` is the canonical current activity/physical-condition field), `offscreenActivity`, presentation, established `currentForm`, numeric player relationship evaluation, and lifecycle/death. Development-owned durable fields remain rejected. New/unknown form definitions are not created by S3.
  * **Prompt continuity:** The injected context is built only from committed Alpha state. It exposes current immediate continuity, relationship axes, read-only established appearance-form IDs/names for `currentForm` selection, and read-only durable context where needed without advertising Development fields as one-pass write channels. The immediate output contract requires one terminal trailer and relationship evaluation for exchange-active NPCs.
  * **Replay and branch safety:** Finalized candidate processing is serialized to prevent concurrent duplicate commits. Memory and durable dedup keys suppress replay across adapter reloads. Committed source fingerprints, swipe IDs, and exact preceding lineage are revalidated against current host history. Replacement/regeneration on an already committed position and prior-branch divergence fail closed rather than layering state; S6 owns history reconstruction/rollback.
  * **Continuation:** SillyTavern continuation appends to the same assistant message position. S3 may remove a prior valid Alpha trailer from the continuation base only when that exact prior dedup key is already durable. Malformed/uncommitted prior transport is preserved and blocks fast mutation. Continuation pending-review identity includes the new assistant fingerprint so the later Development handoff does not collide with the earlier source revision. Foreign `extra.display_text` ownership is preserved.
  * **Transport-only rendering:** After a checked durable commit succeeds, Alpha temporarily stages only `message.extra.display_text` so SillyTavern's first `addOneMessage()` render does not flash the machine trailer. Raw `message.mes` and swipes remain untouched. On `CHARACTER_MESSAGE_RENDERED`, Alpha performs durable-key reconciliation and restores only its temporary display metadata. Existing foreign display overrides are not overwritten. Reload/chat-change reconciliation hides only transport proven by durable dedup state; uncommitted transport is never presented as synchronized success.
  * **Checked SillyTavern persistence:** `SillyTavernStorageAdapter` stores the existing S2 state under `chatMetadata[npc_state_alpha.v1]`. Because SillyTavern's public save wrapper can swallow errors, S3 uses the official same-origin `/api/chats/save` or `/api/chats/group/save` endpoint directly with host request headers and requires both HTTP success and `{ok:true}` before reporting commit success. Character saves retain the normal host chat header and target identity; group saves use the actual group chat file ID (`group.chat_id`), not the selected group entity ID. Server integrity checks and Alpha revision CAS both remain active. Client metadata/cache advance only after acknowledgement and only if the active chat still matches the captured target after the awaited save.
  * **Development handoff only:** Successful one-pass commits persist immutable pending Development source references and fingerprints needed by S4. S3 performs no Development provider call, review, cadence, batching, queue execution, retry orchestration, or durable Development-field automatic write.
  * **Diagnostics:** Bounded diagnostics record host candidate/accept/reject, trailer parse status, commit success/failure, replay suppression, generation stop, and chat switch without creating a second authority or raw-chat store.
  * **Packaging:** `npm run package` builds `dist/` with only `manifest.json`, `index.js`, `LICENSE`, and the runtime `src/` tree. `dist/` and `node_modules/` are ignored in Git.

* **S4 — Asynchronous Development Review Vertical:** Implemented and verified as the final local S4 candidate pending the acceptance commit.
  * **Single settings owner:** `src/contract/settings.js` defines Alpha settings schema v1, Development enabled/defaults, cadence default **3** with range **1–10**, response limit normalization, selected Development connection profile, and the **six-exchange** request cap.
  * **Pending Development scheduler:** `DevelopmentReviewQueue` consumes the S3-persisted pending ledger oldest-first, gives newly admitted NPCs early review, applies cadence to established NPCs, coalesces duplicate triggers, keeps at most one in-flight Development request per chat, and chains only successful bounded batches so backlog drains without unbounded requests or failure spin loops.
  * **Foreground priority:** S3 remains the foreground owner. Starting foreground generation aborts only the same-chat background Development request through `AbortController`; the foreground path never awaits Development work.
  * **Provider boundary:** S4 uses SillyTavern 1.18.0 `ConnectionManagerRequestService` with an explicitly selected host connection profile and non-streaming cancellable requests. Missing/deleted profiles fail closed or pause review. S4 does not copy credentials, expose secrets, or silently fall back to another provider/profile. A separate uncancellable use of the active foreground connection is intentionally not fabricated.
  * **Selective context:** Development prompts contain only exact pending owned narrative sources, the target NPCs’ current durable comparison state, compact recent observations/accepted support, relevant read-only relationship/form state, locks, and the complete durable-domain menu. Alpha transport is stripped from narrative evidence.
  * **Target/source firewall:** Every response target, receipt, concrete source, observation, and support proposal must stay within that target’s supplied batch scope; one target cannot borrow another target’s evidence.
  * **Late-result safety:** Dispatch freezes exact source dependencies and relevant field revisions before provider wait. After the provider returns, current host evidence is reacquired and dependencies are revalidated. Changed sources invalidate only affected pending entries; unaffected targets are freshly re-reviewed rather than committing from a partially stale response.
  * **Field-scoped latest-state commit:** Development writes through the existing shared `CommitCoordinator`. Direct and cross-field read dependencies defer only affected durable fields, preserving newer S3/live state. Relationship-dynamic changes depend on relationship evaluation; appearance evolution depends on current form; lifecycle dependencies are rechecked where applicable.
  * **C08 stale safety:** Observation-only and support-only Development work now participates in the same field-revision dependency check. Stale observations/support are not persisted, receipts become deferred, and pending work remains recoverable.
  * **Atomic pending bookkeeping:** Pending resolution occurs in the same CAS transaction as Development proposals, observations, accepted support, and review receipts. Deferred/failed/unavailable status is persisted as runtime-owned pending metadata; successful reviewed scope is removed only with a matching non-deferred receipt.
  * **Reload/recovery:** Pending work is durable in `npc_state_alpha.v1`; scheduler/provider instances are ephemeral. Re-instantiating storage/coordinator/queue resumes the durable pending ledger. Provider failures do not tight-loop automatically; manual retry or fresh evidence can make work eligible again.
  * **Stage boundary:** No S5 dossier/settings UI, S6 history reconstruction/import path, or later-stage implementation was added.
